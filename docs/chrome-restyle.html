Neurite chrome, measured against Excalidraw

A proposal. Nothing here is implemented. Every Neurite number is measured out of a running instance at commit e0e48c0; every Excalidraw number is read out of excalidraw/excalidraw@master.

1. The verdict

Neurite's chrome is already the same shape as Excalidraw's: floating rounded islands over a full-bleed canvas, a hamburger at top-left, a tool pill centred at the top, 24×24 stroke-2 Lucide icons, and instant custom tooltips. Several metrics match to the pixel — the menu row's gap: 10px, its font-size: 14px, its 16px icons, and the panel's 8px radius are all exactly Excalidraw's values already.

So this is not a rebuild. Four things separate the two, and only one of them is a real decision:

GapWhat it costsKind
Islands read as cut-out panels: a 1px hairline, one heavy black shadow, and a blur behind them~20 lines of CSScosmetic
Dark only. Excalidraw is light-first with a dark theme; Neurite has no light theme and cannot get one — 486 colour literals are hardcodedChrome band only: ~350 lines. Whole app: not worth itmechanical

4. What cannot be lifted

The components. Excalidraw is React + TypeScript + SCSS compiled by Vite. Neurite has no bundler and no React: index.html loads js/main.js, which fetches ~83 files sequentially into one shared global scope. Nothing under packages/excalidraw/components/ can be dropped in. What transfers is the token set, the metrics, and the layout grammar — all of which are plain CSS.
Excalifont. The hand-drawn canvas font. The repository's root LICENSE is MIT, but the font binary's own copyright table reads Copyright (c) 2024 by Excalidraw. All rights reserved. and there is no per-font licence file beside it. Mixed signal, and it is out of scope anyway: it is canvas text, not toolbar. Assistant, the font the chrome actually uses, is a different matter — it is on Google Fonts under the OFL (verified), so it is safe to adopt.

Attribution. Excalidraw is MIT, Copyright (c) 2020 Excalidraw; Neurite is MIT too. Copying token values and metrics is compatible. If CSS is lifted rather than re-derived, the file should say where it came from.

5. The one real decision

Excalidraw's toolbar is a mode picker. You press R, the rectangle button stays lit, and every click on the canvas draws a rectangle until you switch. Neurite's toolbar is a one-shot creator: click the note icon and a note appears immediately, or drag the icon out to place one. Nothing stays armed and no button ever looks active.

The Excalidraw look depends on that active state — the lit pill is the single most recognisable thing about the toolbar. Adopting the look without the behaviour means a toolbar with a highlight that never appears.

Try

Three ways to answer it

OptionWhat happensCost
A. Look only Take the tokens, metrics, digit badges and shortcut hints. Tools keep firing on click. The active state is used for hover and focus only. CSS + markup. No JS behaviour touched.
B. Armed tools recommended Clicking a tool arms it; the next canvas click places one node there and disarms. 1–4 arm, Esc disarms. Drag-out keeps working untouched. The lit pill becomes real. One armed-tool variable, one canvas click handler, one class toggle. The digits already exist in the tooltips.
C. Full modal The tool stays armed across many placements, like Excalidraw. Every canvas click makes a node until you press Esc. Fights Neurite's canvas: click-drag pans, and double-click already creates. A mode that swallows clicks would need those renegotiated.

B because it buys the whole visual grammar for one variable and one handler, and because it is reversible. C collides with panning, which is the gesture the fractal depends on most.

6. Phases

Phases 1–3 are CSS only, and that is a measured claim rather than a hope: exactly four files under js/ mention any chrome class name at all (dropdown.js, savenet.js, handledrop.js, record/record.js), and the only class any of them writes onto the chrome is open, toggled at dropdown.js:183. Nothing reads a colour, a radius or a size out of the DOM. Phase 4 is the only one that touches behaviour.

  1. Tokenise the chrome band, and nothing else

    The chrome is a contiguous ~350 lines: styles.css:1221–1530 (tool bar, menu button, dropdown, menu rows), 4206–4260 (.tool-bar-action) and 4651+ (.panel-icon). Replace the literals there with tokens — today .tool-bar and .dropdown-content both hardcode #1a1921f2 and 1px solid #8882 while --ui-surface exists and is read exactly once. Also fold the second :root at line 3178 in, and delete styles.css:2994 — a bare #disk-file-button { font-size: 13px }, sitting 1,500 lines away from the .menu-row rule it overrides, which is why Save to… renders a pixel smaller than every row beside it.

    One trap. Do not reach for * { box-sizing: border-box } while tidying this band. test/menu-keyboard.test.js asserts no universal block declares box-sizing, because .menu-button carries an explicit content-box to undo the UA's border-box on a <button> and keep its 42×42. A universal reset changes what that rule is compensating for and fails the suite. The * {} block already exists at styles.css:77, which makes it an easy place to add one by habit.

    no visual change · pure prerequisite · pins: computed styles unchanged before/after

  2. Retune the island

    Drop the 1px hairline. Swap the single heavy shadow for the 3-layer one. Lighten #1a1921f2 toward #232329 and drop the backdrop blur, which is doing nothing at 95% opacity but costs a compositor layer over an animating canvas. Radii to 8/6.

    visible · ~20 lines · the biggest look change per line spent

  3. Menu row anatomy

    Add the right-aligned shortcut hint at opacity: .5. The shortcuts already exist in data-tooltip prose — surface them. Row height 34→32, radius 5→6, hover fill tinted with the accent instead of flat white. Keep the chevron on panel rows: it is the one thing that says "this opens something", which Excalidraw solves with a submenu arrow anyway.

    visible · ~15 lines + markup per row

  4. Digit badges and the armed state

    Print 1–4 in the corner of each tool button. Then option B above: arm on click, place on the next canvas click, Esc to cancel. This is the phase that needs a decision before it starts.

    behaviour · needs sign-off · browser-verify before writing the test

  5. A bottom-left zoom island

    Nothing reports the view on the canvas itself. The #pan and #zoom boxes are inputs rather than readouts — typing in one moves the view — and they are inside the Views panel (viewstab.html:44,48); the FPS counter is inside the Fractal panel (fractaltab.html:49). Excalidraw keeps zoom at bottom-left, where it doubles as the reset control.

    Cheaper than it looks, and only if the island is built as a child of .dropdown (dropdown.html:13). That root is already 100vw × 100dvh, pointer-events: none, at z-index: 100 — its own comment at styles.css:1195 says it is sized in viewport units precisely because inset: 0 put "every bottom-anchored island above the top edge of the screen". So a child gets three things free: the band over canvas and cards, pointer-events: auto from .dropdown > * (styles.css:1214), and the guard at dropdown.js:296 that stops mousedown, wheel and dblclick over chrome from panning and zooming the graph. Built anywhere else, all three have to be re-solved by hand. The change is bottom and left on one element.

    new region · optional · check it against the iPad work in ipad-spike.md first

The two regions with no Neurite counterpart

Five surfaces a reader can point at; Neurite has three of them. That grouping is this page's, not Excalidraw's — its own taxonomy is coarser, three docks ("top" | "bottom" | "side") and two measured panels ("sidebar" | "stylesPanel", types.ts:1426,1506), with the top-left menu and the top-centre tools both living in one App-menu_top row (LayerUI.tsx:309,347). The missing pair is worth naming so neither gets mistaken for something this proposal covers:

Excalidraw regionNeuriteIn scope?
Main menu, top-left.menu-button + .dropdown-contentyes — phases 1–3
Tool island, top-centre.tool-baryes — phases 1–4

Properties island, left — stylesPanel in Excalidraw's own source: stroke, background, fill, width, opacity, layers, whenever a shape is selected none. Nothing under js/ shows or hides a chrome surface on node selection; per-node configuration lives entirely inside each node's own window chrome no
Library, top-rightnoneno

The properties island is the surface Excalidraw users touch most, and its absence is the largest structural difference between the two apps — but it is neither the toolbar nor the menu, and Neurite's equivalent decisions already live on the node. Raising it here only so it is not discovered later and read as an omission.

z-index reads as ad hoc and mostly is not. Sixteen distinct values across styles.css — -1, 0, 1, 2, 4, 10, 20, 30, 100, 150, 500, 900, 1000, 1001, 2000, 9999 — but the large numbers are local. .dropdown is position: fixed with z-index: 100 (styles.css:1195), which makes it a stacking context, so .dropdown-content at 1, .menu-button at 2 and .menu-icon at 10 only ever compete with each other. The same trick hides inside .window, which stacks at 2 while .ainode-settings-container sits at 100 and .title-input-wrapper at 150 within it. So there is no global ordering to reason about, and a new island needs no new z-index value at all — see phase 5.
One idea worth stealing that is not visual. Excalidraw tags each island data-viewport-ui and measures them in getViewportOffsets, so the canvas knows which rectangles are covered. Neurite has nothing like it, which is why a "fit to view" can drop a node under the tool pill. Independent of the restyle, and cheap.
What this proposal does not do. It does not tokenise the other ~4,900 lines of styles.css, and it does not deliver a light theme. The :root block's own comment already settled that direction — tokens are added as the rules that need them are touched, and a single-pass rewrite is explicitly not the goal. A light theme would reverse that decision, and it should be argued on its own merits, not smuggled in as part of a restyle.
